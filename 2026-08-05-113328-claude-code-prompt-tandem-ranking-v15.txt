  ## Context                                                                    
                                                                                
  You are building the ranking and interest-modelling layer for **Tandem**, a   
  social app where users post local activities ("tandems") that others nearby   
  can join. The product is aimed at platonic companionship, not dating. The     
  north star metric is **repeat-tandem rate**, not joins or session time.       
                                                                                
  The full design lives in `tandem-matching-v2-framework.md` in this repo.      
  **Read it fully before writing any code.** This prompt scopes and constrains  
  that document; where they disagree, this prompt wins.                         
                                                                                
  Current state: roughly 40 beta users, Supabase backend, ranking currently     
  runs client-side at fetch time over already-loaded activities. Assume a React 
  + Supabase client, but see the hard constraint on framework independence      
  below.                                                                        
                                                                                
  ## Scope                                                                      
                                                                                
  Build framework steps **1, 2, 3, and 5** only:                                
                                                                                
  1. Schema migration + instrumentation (`expand` events, retrieval `source`    
  tags)                                                                         
  2. The interest state model (event log, per-source decay, saturation, novelty 
  prior)                                                                        
  3. Retrieval stage + slate assembly                                           
  5. Explicit interest statements                                               
                                                                                
  ## Explicit non-goals — do not build these                                    
                                                                                
  - **Graph consumption.** Write `graph_edges` rows via trigger, but            
  `graphAffinity` returns `0` and the `graph` retrieval source returns `[]`.    
  Leave both as clearly-marked stubs with the intended signature.               
  - `revealed`/`desired` split and intent gap (framework §1.5) — needs `expand` 
  data that doesn't exist yet. Emit the events; don't consume them.             
  - Transition detection (§1.6) — needs 120 days of history.                    
  - Any learned weights, regression, or embeddings.                             
  - Server-side ranking or Supabase RPCs. Everything runs client-side.          
  - Any UI. Export a clean interface; do not touch existing components.         
                                                                                
  Build the *seams* for the non-goals — correct types, stub functions with real 
  signatures, no dead abstraction.                                              
                                                                                
  ## Hard constraints                                                           
                                                                                
  1. **The core is framework-agnostic.** Nothing under `src/ranking/core/` may  
  import from React, React Native, Expo, Supabase, or any browser or native     
  global. Pure TypeScript, pure functions, no I/O, no `Date.now()` — time is    
  always an injected parameter. This is non-negotiable; it is what makes the    
  module testable and what protects it from a pending stack decision.           
  2. **All tuning constants live in one exported object** in                    
  `src/ranking/core/constants.ts`. No magic numbers anywhere else. Every        
  constant gets a one-line comment saying what it does and what raising it      
  would do.                                                                     
  3. **Determinism.** Given the same inputs and the same seed, output is        
  byte-identical. The random retrieval source uses a seeded PRNG (mulberry32 or 
  similar, implemented inline — no dependency) seeded on `userId + sessionId`.  
  4. **The score orders, never filters.** An empty deck may only result from    
  user-applied time pills. If scoring throws, log and fall back to              
  proximity-sorted order — never an empty deck.                                 
  5. **No new runtime dependencies** beyond what's in `package.json`. Dev       
  dependencies for testing are fine.                                            
  6. **The numeric score is never returned to any UI-facing type.** Debug       
  output is behind an explicit `{ debug: true }` option.

  ## Interest state — implementation notes                                      
                                                                                
  Implement framework §1.1–1.4 and §1.7 exactly as specified. Specific          
  requirements:                                                                 
                                                                                
  - The source weight/half-life table (§1.2) is data in `constants.ts`, not a   
  switch statement.                                                             
  - `sat(x) = x / (x + k)` and the novelty term are separate, individually      
  testable pure functions.                                                      
  - `computeInterestState(events, now)` returns the full vector plus, for each  
  metric, the top contributing events — the explanation layer needs provenance, 
  and you cannot reconstruct it afterwards.                                     
  - `user_interest_state` is a **cache, not a source of truth.** It must be     
  fully rebuildable from `interest_events` alone. Include a function that does  
  exactly that, and a test asserting cache and rebuild agree.                   
  - Explicit statements (§1.7): `recordExplicitStatement(userId, metric,        
  polarity)` writes weight 1.0. Structured and reversible — the row must be     
  listable and deletable by the user. Do not build any NLP; the caller passes a 
  resolved metric slug.                                                         
                                                                                
  ## Backfill script                                                            
                                                                                
  `scripts/backfill-interest-events.ts` derives `interest_events` from existing 
  data so current users don't cold-start on ship day:                           
                                                                                
  - one `post_created` event per authored activity, at its original             
  `created_at`                                                                  
  - one `join_requested` per join request, one `tandem_completed` per           
  completion, original timestamps                                               
  - onboarding answers (`ideal_saturday`, `tandem_intent`) mapped through the   
  existing static table to `onboarding` events at account creation time         
                                                                                
  Tag every backfilled row `source_meta = 'backfill'` so they can be excluded   
  once organic data accumulates. Idempotent — safe to run twice. Dry-run flag   
  that prints counts per user and writes nothing.                               
                                                                                
  ## Tests                                                                      
                                                                                
  Vitest or Jest, whichever the repo already uses. Not exhaustive coverage —    
  targeted tests on the things that will actually break:                        
                                                                                
  - decay: an event at exactly one half-life contributes half its strength      
  - saturation: the 40th event of a metric moves `interest` by less than 1% of  
  what the 1st did                                                              
  - novelty: a metric with 2 events from 5 days ago outranks one with 40 events 
  spread over 200 days                                                          
  - determinism: same seed, same deck, ten runs                                 
  - fallback: scoring throwing produces a proximity-ordered non-empty deck      
  - slate constraints: no more than 2 same-category cards in a deck of 8; at    
  least one `fresh_host` in the top 3                                           
  - cache/rebuild agreement                                                     
  - **cold start**: a user with zero events and zero completions produces a     
  sane non-empty deck driven by proximity and onboarding answers                
                                                                                
  Fixtures are hand-built and committed. No random generation in tests.

  ---                                                                           
                                                                                
  ## Why this exists                                                            
                                                                                
  Your simulator found that a pure proximity baseline beats the full ranker on  
  repeat rate by 7–14% at 40 users. That result is correct and this change is   
  the response to it. The interpretation is not "the ranker is bad" — it is     
  "the ranker is calibrated for a density Tandem does not have yet."            
                                                                                
  At 40 users with ~12 live posts, a viewer can see the entire eligible pool in 
  a week. When the pool is enumerable, ordering barely matters (everything      
  gets shown regardless), exploration quotas cost real slots for zero           
  informational gain (the explore card would have been seen anyway), and        
  `interest(u, m)` is computed from so few events that it contributes more      
  variance than signal. Meanwhile the actual failure mode at that size is a     
  host posting, getting zero joiners, and never posting again. Three of those   
  and supply collapses.                                                         
                                                                                
  So the objective itself changes with density:                                 
                                                                                
  - **Low density — the binding constraint is liquidity.** Optimise for *every  
  post getting at least one joiner*. This is a global assignment problem, and   
  at 40 users global optimisation is tractable.                                 
  - **High density — the binding constraint is attention.** Optimise for *every 
  viewer getting a good card*. This is greedy per-viewer ranking, which is      
  what the existing code does.                                                  
                                                                                
  Greedy ranking is only necessary because global assignment doesn't scale.     
  Build the algorithm so it approximates assignment when it can and degrades to 
  ranking when it must.                                                         
                                                                                
  ## The hard constraint on how you build it                                    
                                                                                
  **One algorithm. No mode switch, no second code path, no boolean flag.**      
                                                                                
  Every affected parameter becomes a continuous function of a density estimate. 
  Village behaviour must be the mathematical limit of city behaviour as         
  density → 0. If a reviewer can find an `if (regime === 'village')` that       
  changes control flow rather than a coefficient, this is built wrong.          
                                                                                
  Rationale beyond elegance: a switch at a user-count threshold produces a      
  visible discontinuity in product feel on a single day, is untestable in the   
  region that matters, and will be flipped wrong at least once.

  P_accept, P_complete and R_repeat are the only viewer-independent terms in the
